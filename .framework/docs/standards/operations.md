# 发布、可观测性与运维规范

本规范适用于需要持续运行或交付给他人使用的服务、应用、数据任务和 AI 能力。纯文档或一次性本地实验可声明不适用部分。MUST 为适用要求，SHOULD 为可调整建议，MAY 为选项；角色可合并，生产责任与操作权限必须明确。

## 1. 服务接管信息

首次生产发布前 **MUST** 提供一份可实际操作的服务说明，至少包含：

- 服务用途、owner、维护时间与联系/升级路径。
- 环境、入口、部署制品、主要依赖、配置和秘密的管理位置。
- 用户关键路径、健康判定、日志/指标入口，以及告警接收人。
- 部署、验证、停止、回滚或前滚命令；每条命令的环境、前提与副作用。
- 数据恢复方式、无法恢复的边界、适用的 RPO/RTO 和最近验证日期。

小型服务可以将这些信息写在一个 runbook 中，无需独立运维平台。命令必须由实际项目验证；本框架里的清单不代表已有运行环境或自动化部署。

## 2. 可观测性与目标

- **MUST** 为关键用户任务选出可测的服务指标，定义成功/失败、分母、时间窗口、目标及负责人。内部可靠性目标与对用户承诺的 SLA 必须区分。
- **MUST** 生产失败能关联到运行环境、制品/代码版本、请求或任务 ID；异步任务能关联排队、执行和完成状态。
- **MUST** 日志对关键失败提供可行动上下文，不记录密码、令牌和不必要的个人数据。遥测访问权限、采样和保存期限遵循[安全规范](security-privacy.md)。
- **SHOULD** 采用结构化日志、指标与 trace；跨服务或复杂 AI 调用可以使用 OpenTelemetry 统一上下文与采集方式。OTel 是采集/处理/导出体系，采用它不自动产生有效告警。[OpenTelemetry signals](https://opentelemetry.io/docs/concepts/signals/)
- **SHOULD** 从少量用户可感知指标建立 SLO，例如请求成功率、可用结果延迟、任务按时完成率。目标根据用户需要、预算和观测基线确定，不机械复制“几个 9”。[Google SRE：SLO](https://sre.google/sre-book/service-level-objectives/)
- **MUST** 每条唤醒负责人的告警有阈值、持续时间、去重、分级和可操作 runbook；不需要人处理的信号应进入看板或后续任务。
- **MAY** 随规模增加采用错误预算和分层告警，但必须明确消耗超限时采取什么动作。

## 3. 发布与环境

- **MUST** 将生产环境和测试环境、账号、数据及秘密隔离；预览环境不能默认读取生产数据。
- **MUST** 发布记录追踪源 commit、制品标识、配置变更、迁移、验证、操作者与时间。尽可能把已验证制品提升到生产，避免部署时重新解析浮动依赖。
- **MUST** 发布前明确项目治理要求的授权范围、观察窗口、成功/失败判据和恢复负责人；生产动作只能在既有授权内执行。
- **MUST** 发布后的冒烟检查覆盖实际关键任务，不能只确认进程存活或 HTTP 返回 200。
- **SHOULD** 使用渐进发布、特性开关或可控批次减少影响；开关需要 owner、默认值与清理日期。
- **MAY** 对规模和风险较低的服务采用简单部署脚本与手工批准；关键是流程可重复、可追踪且能恢复。

每次有用户可见、契约、配置或数据影响的发布，使用[发布记录](../../templates/artifacts/release.md)记录变更与验证；相关测试门禁见[测试规范](testing.md)。

## 4. 数据迁移与恢复

- **MUST** 数据迁移有版本、执行顺序、前置条件、影响评估、失败处理与执行记录；说明锁表/长事务、容量、兼容旧应用及重复运行风险。
- **MUST** 破坏性迁移在代表性数据上演练，并在执行前确认备份或其他可行恢复路径。备份不是跳过授权或测试的理由。
- **MUST** 区分代码回滚和数据恢复。旧代码无法读取新数据时不能直接回滚；应采用兼容过渡或经验证的前滚/补偿方案。
- **MUST** 需要持久化保护的数据定义 RPO（可接受的数据损失时间窗口）和 RTO（可接受的恢复时长），据此选择备份频率、保留期、存储与权限。
- **MUST** 首次承载需保护的生产数据前完成恢复验证；之后按项目风险规定周期，并在存储、加密密钥或恢复机制重大变化后重新验证。
- **MUST** 恢复演练验证数据可读、业务一致性、权限与目标恢复时长；“备份任务成功”不等于可恢复。
- **SHOULD** 在隔离环境恢复，避免覆盖生产数据或发出真实邮件、支付、Webhook 等副作用。

数据可重新生成、无持久状态或由第三方负责时，可声明相应条目不适用，但 **MUST** 说明实际责任边界；供应商提供备份能力不代表已覆盖应用恢复。

## 5. 故障 runbook

每个影响关键路径的主要故障类型 **MUST** 有足够指导处理的 runbook。一个文件可覆盖多个类型：

| 内容 | 需要写清的事实 |
| --- | --- |
| 触发 | 告警、用户表现、如何确认影响，哪些现象可能误报 |
| 诊断 | 看哪些指标/日志、如何区分依赖/应用/数据问题 |
| 止损 | 可在什么授权内限流、关功能、停队列或切只读 |
| 恢复 | 回滚/前滚/重放步骤及条件，避免重复副作用 |
| 验证 | 关键路径与数据一致性如何恢复到可接受状态 |
| 升级 | 谁决定扩大操作范围，何时需要数据或安全负责人 |
| 证据 | 时间线、变更版本、相关 ID 和已做操作，须脱敏 |

**MUST** 紧急操作遵循[治理](../handbook/governance.md)中已建立的事故授权，超出范围时按升级路径处理。**SHOULD** 对重大事故和重复故障进行复盘，产出可跟踪的修复与预防任务；聚焦系统原因、检测和恢复能力。

## 6. 容量、费用与 AI 运行

- **MUST** 资源、存储、第三方配额和模型费用有预算或上限，能发现异常增长；批处理有超时、并发与重试约束。
- **MUST** 任务重放、消息补偿和批量重试前检查幂等、数据范围和外部副作用。
- **SHOULD** 关键路径监测队列积压、连接池、存储增长及依赖限额，按实际风险规划容量。
- **MUST** AI 服务能定位到模型/提示/工具/检索版本，并具备停止自动动作、限制成本、降级或人工接管入口。不能把模型 API 正常等同于业务质量正常。

## 7. 验收与裁剪

生产发布的最小验收是：有人负责、可判定健康、可找到失败、知道如何恢复、适用的数据恢复已验证、操作在授权范围内。高风险项目按[测试风险分级](testing.md)增加独立复核、演练和发布保护。

原型阶段可以先保留一页操作说明和手工检查；对外服务或处理真实数据后，必须重新评估适用要求。MUST 的临时例外使用[例外模板](../../templates/artifacts/exception.md)，明确负责人、补偿措施、风险接受者、到期与复核条件。
