# 技术架构、选型与契约规范

架构的目标是以可承担的复杂度实现产品能力，并保留必要的演进空间。MUST 是适用要求，SHOULD 是可调整建议，MAY 是选项。本框架统一决策方法与兼容边界，不要求所有项目选择同一套技术。

## 1. 先写能力与约束

新项目首次技术选型，以及涉及显著依赖、部署、数据或边界变化时，**MUST** 在[技术设计](../../templates/artifacts/technical-design.md)中回答：

| 输入 | 需要具体到什么程度 |
| --- | --- |
| 核心能力 | 用户任务、领域对象、状态变化、关键业务不变量 |
| 规模假设 | 用户量、并发、数据量、增长预期；未知项及验证方式 |
| 质量目标 | 关键路径延迟、可用性、恢复目标、无障碍及离线需求 |
| 数据约束 | 敏感级别、归属、保留期、地域/租户边界、删除要求 |
| 外部依赖 | 身份源、第三方服务、现有接口、模型、供应商限制 |
| 团队与资源 | 维护人数、已有能力、开发周期、预算及值守能力 |
| 演进约束 | 哪些必须兼容，何时允许破坏性改变，预期退出路径 |

**MUST** 区分已验证事实、假设与待研究问题；会改变选型的未知项先用有时间边界的调研或原型验证。架构图与选型表不能替代业务不变量和失败语义。

## 2. 选型决策

- **MUST** 对关键选择比较至少一个可行替代方案，或说明只有一个方案满足硬约束。比较维度包括适配能力、维护复杂度、总成本、生态与安全维护、许可证、可观测性及迁移成本。
- **MUST** 记录选定版本、支持窗口的核验日期、工具链兼容性、部署约束和升级责任。使用“最新”“长期支持”等描述时，附可核验来源与日期。
- **MUST** 将跨模块、难逆转或长期影响的决策写成 [ADR](../../templates/artifacts/adr.md)：上下文、备选、决策、代价、验证证据和重审触发条件。
- **SHOULD** 以模块化单体作为小团队业务系统的初始候选；只有在独立伸缩、隔离、合规边界或组织边界等实际需求下增加服务拆分。这是本框架的可更改建议，不是行业唯一正确架构。
- **SHOULD** 优先减少必须自建和运维的组件；托管服务也需评估数据、费用、配额、退出和故障边界。
- **MAY** 使用微服务、事件驱动、Serverless、端侧计算或本地模型，但需写明其解决的具体约束以及增加的复杂度。

规模较小的选择可在一页技术设计中完成；不需要为每个包建立 ADR。新证据推翻决策时新增替代决策并链接旧 ADR，保留历史原因。

## 3. 边界与依赖

- **MUST** 提供系统上下文图和主要模块/部署单元图，标出用户、外部系统、存储、信任边界与数据流。项目简单时两张图可以合并。
- **MUST** 每个核心数据对象有明确的写入责任方；不得在多个项目中各自修改同一业务事实而没有一致性规则。
- **MUST** 说明同步调用、异步事件、批处理或直接库调用的选择，并定义超时、失败、重试、幂等、顺序与取消的适用语义。
- **MUST** 领域不变量在可信执行层保证；前端状态、缓存和模型推断不能充当权限、资金或数据一致性的唯一保护。
- **SHOULD** 保持模块接口小而稳定，把多步骤协作与错误处理收敛到拥有该能力的模块内。
- **MAY** 用适配器隔离变化频繁或需要替换的供应商；只有一个稳定依赖时，不必为了假想替换建立多层框架。

## 4. API、数据与事件契约

对外、跨项目或跨团队使用的接口 **MUST** 有版本化契约和 owner。项目内部简单函数可用语言类型和测试表达；不要为所有函数生成接口文档。

| 契约 | MUST 记录的内容 |
| --- | --- |
| HTTP API | 路径/方法、请求响应、字段语义、验证约束、认证授权、错误、分页、幂等与限流；明确哪些适用 |
| 数据模型 | 主键与标识稳定性、单位/时区/精度、null 与缺省含义、约束、索引意图、保留/删除与迁移 |
| 事件 | 名称、生产者/消费者、schema 与版本、事件 ID、业务发生时间、顺序、重复、重放、幂等和死信处理 |
| 共享库/SDK | 公共入口、兼容运行时、版本策略、错误模型、废弃窗口、消费者验证方式 |

- **SHOULD** HTTP API 使用 OpenAPI 或项目工具链可靠支持的等价机器可读定义。OpenAPI 描述 HTTP 接口，不能独立证明实现满足权限、业务不变量或兼容性。[官方规范](https://spec.openapis.org/oas/v3.2.1.html)
- **MUST** 区分“描述格式的版本”和“业务接口的版本”，锁定校验器/生成器支持的版本；标准新版本发布不构成自动升级理由。
- **MUST** 契约变化检查实际消费者影响：删除字段、收紧约束、修改默认值、改变状态码/单位/权限、扩展枚举等都可能影响消费者。新增字段也要验证严格解析器的行为。
- **MUST** 破坏性变更提供迁移说明、支持窗口、消费者负责人及验证结果。无法兼容时明确新版本入口或协调切换方案。
- **MUST** 数据迁移和部署版本有兼容顺序；增加字段、迁移数据、切换读写、移除旧字段可分步进行，删除操作需要恢复或补偿设计。

## 5. AI 能力的架构位置

产品包含模型能力时，**MUST** 划定模型输入输出、检索、工具执行、记忆、评估和审计的责任。身份和授权由应用可信层执行；模型只提出动作或生成候选内容。工具动作的结果由外部真实状态确认。

**SHOULD** 从规则或简单工作流验证能否完成任务，再比较引入模型、RAG 或多 Agent 的必要性；复杂编排应有成功率、成本、延迟或能力上的证据。模型不可用、超预算、上下文不足和输出不合格时的退路必须进入设计，详见 [AI 工程规范](ai-engineering.md)。

## 6. 跨项目一致性与复用

- **MUST** 共享领域词汇、标识、契约和版本信息；同时允许产品有各自的部署与发布节奏。
- **MUST** 提取共享组件前明确 owner、消费者、支持范围、发布位置、兼容与废弃策略。复制代码应记录来源版本，并承认复制后需要各自维护。
- **SHOULD** 优先复用稳定契约、领域能力与成熟组件，再复用实现细节；避免“公共工具库”无限吸收无关职责。
- **SHOULD** 新项目先检查现有能力目录，评估复用、适配或新建，并记录选择理由。流程见[复用与升级](../handbook/reuse-and-upgrades.md)。

## 7. 架构验收与例外

实现前 **MUST** 有足够支撑当前风险的设计证据；实现发现新约束时，更新 spec/技术设计/ADR 后继续。高风险架构变更在[测试计划](../../templates/artifacts/test-plan.md)中覆盖关键不变量、兼容消费者、失败与恢复情形。

上线前至少能回答：如何部署、如何定位失败、如何恢复、如何演进数据、如何判断目标达成。架构 owner 对当前边界和未解决问题签署结论，不以图的数量作为验收标准。MUST 的临时例外按[治理](../handbook/governance.md)使用[例外模板](../../templates/artifacts/exception.md)，包含替代措施、负责人和到期日。
