# 测试流程与质量规范

测试用于证明特定风险已受控。MUST 是适用要求，SHOULD 是可说明原因后调整的建议，MAY 是可选手段。本文件定义通用变更风险；项目采用档位 lean/product/platform 不决定变更风险，单人项目也可能有高风险操作。

## 1. 变更风险分级

每个任务 **MUST** 评估影响、可逆性、暴露范围与不确定性，按最高适用风险选择等级。无法判断时先补充证据，不能自动归为低风险。

| 风险 | 常见条件 | 最小证据 |
| --- | --- | --- |
| `low` 低 | 文档、纯样式、无业务语义变化的局部调整，容易恢复 | 相关静态检查或内容/视觉核对；可重复的人工检查也可 |
| `medium` 中 | 新业务分支、接口接入、可恢复数据写入、常规依赖升级 | 受影响规则的自动化验证、边界或集成验证、关键路径回归 |
| `high` 高 | 身份/权限/租户隔离、资金、不可逆迁移、敏感数据、共享破坏性契约、对外高影响 Agent 操作 | 书面测试计划、独立审阅、故障与滥用测试、恢复演练，以及发布控制证据 |

高风险标识不意味着每种测试都必须执行。负责人 **MUST** 在[测试计划](../../templates/artifacts/test-plan.md)中选择能覆盖具体风险的方法，说明其他方法为何不适用。单纯文件数量、行数和模型置信度不得替代风险判断。

## 2. 验收与测试设计

- **MUST** 从 [spec](../../templates/artifacts/spec.md) 的可观察验收条件生成用例；建立“验收条件 → 风险 → 测试/人工验证 → 结果”的追踪关系。
- **MUST** 用例包括适用的正常路径、边界值、错误路径、无权限、超时、重复请求、并发或部分失败；按功能特征裁剪。
- **MUST** 业务缺陷修复增加可复现原故障的回归证据；若自动化成本不合理，记录稳定复现步骤、人工检查方式与理由。
- **SHOULD** 自动化回归在修复前能失败、修复后通过；不能保留失败版本时，记录原故障复现证据。
- **MUST** 验证真实结果，例如数据库状态、权限隔离、已发送事件或用户可见结果；只断言 mock 被调用、快照未变化或代码内部函数名不足以证明业务成立。
- **SHOULD** 选择覆盖相同风险的最小、稳定测试层级；避免多个层级机械重复全部用例。

## 3. 各层测试的职责

| 类型 | 重点 | 使用时机与边界 |
| --- | --- | --- |
| 单元 | 领域规则、转换、状态机、边界值 | 纯规则优先；不要求把简单转发函数逐一测试 |
| 集成 | 数据库约束、事务、序列化、权限和外部适配器 | 有边界行为时使用可控的真实服务；mock 无法证明实际连接和方言兼容 |
| 契约（contract） | 请求/响应、事件 schema、共享 SDK、生产者/消费者兼容 | 对外或跨项目契约改变时 MUST 验证；结构校验之外还需检查语义变化 |
| E2E | 用户完成关键任务，跨层协作 | 覆盖少量重要旅程；不是所有边界条件的主要承载层 |
| 手工与探索 | 视觉、键盘、屏幕阅读器、未知行为、复杂恢复 | UI 或高影响流程变化时按范围执行并记录 |
| 性能与韧性 | 延迟、吞吐、容量、限流、超时、重试、恢复 | 有性能预算或故障风险的变更执行；不能用本地一次测量宣称生产容量 |
| 安全 | 授权、租户隔离、秘密、注入、依赖风险 | 针对实际攻击面设计负向用例，见[安全规范](security-privacy.md) |
| AI eval | 输出质量、任务成功、工具副作用、拒答、成本与波动 | 产品模型、提示、检索或工具策略改变时适用 |

测试分层借鉴 [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html) 对 E2E 成本与反馈速度的讨论。其测试比例是经验起点；本框架不规定固定比例，也不要求全仓 100% 覆盖率。覆盖率用于发现遗漏，不能代替风险与验收证明。

## 4. 测试数据与执行可靠性

- **MUST** 测试可隔离执行、可清理，默认不对生产系统写入；真实第三方服务的验证使用专用测试账号及明确预算。
- **MUST** 数据集有来源、使用权限和脱敏说明，不把生产秘密或可识别用户数据直接提交到仓库。
- **MUST** 时间、随机数、环境变量和外部依赖的不可控部分有处理方案；不能依赖测试执行顺序。
- **MUST** 保留首次失败证据。重跑变绿不等于问题解决； flaky 测试隔离须有负责人、原因、到期时间和替代验证，不能静默跳过质量门禁。
- **SHOULD** 记录失败日志、最小复现输入及适用的截图/trace，同时遵循脱敏与保留期限。
- **MAY** 根据故障分布采用属性测试、模糊测试、变异测试或故障注入，不以工具数量衡量质量。

## 5. AI eval 与确定性检查

完整要求见 [AI 工程规范](ai-engineering.md)与[评估模板](../../templates/artifacts/eval-plan.md)。

- **MUST** 将 schema、权限、工具参数、资源预算等可确定的约束交给程序检查，不能仅让另一个模型评判。
- **MUST** 在变更前固定评估用例、评分规则、阈值、运行次数与基线；展示失败类别和样本，不只汇报总分。
- **MUST** 隔离开发调优集与保留评估集，评估时不把答案交给被测系统；按重复运行观察非确定性，不能把单次成功作为稳定性证明。
- **MUST** 涉及外部动作时验证实际状态与越权拦截；“模型回答已执行”不算执行成功。
- **SHOULD** 用人工抽样校准模型评分，分开报告能力改进与既有能力回归；高风险失败不能被平均分掩盖。

## 6. 从本地到发布的闸门

以下是业务项目需要实现的目标流程；本方法论仓库自身的文档/脚手架检查不等于下列业务 CI 已配置。

| 阶段 | MUST 满足的条件 | 证据位置 |
| --- | --- | --- |
| 本地变更 | 受影响静态检查与最小验证通过，或准确记录环境阻塞 | ticket / PR |
| PR 合入 | 对应风险所需检查通过；契约、迁移、UI、AI 等适用检查完成；所需审阅完成 | CI 运行与评审记录 |
| 候选发布 | 对待发布 commit/制品完成所需集成和冒烟；环境配置、迁移与恢复方案已验证 | [发布记录](../../templates/artifacts/release.md) |
| 生产发布 | 在项目授权范围内执行；观察窗口、停止条件、回滚/前滚负责人明确 | 发布记录 / runbook |
| 发布后 | 检查关键用户路径、错误率和数据一致性；异常进入事件处理 | 观察结果 / 问题记录 |

**MUST** 对失败检查作出真实处理：修复、确认不适用，或完成带风险接受人的限时例外。不得通过修改阈值、只挑通过用例或重新定义“通过”掩盖回归。紧急修复走项目[治理流程](../handbook/governance.md)，补做验证必须有具体负责人和期限。

## 7. 适用与例外

低风险内容修改可以只检查内容和链接，无需新增业务测试。原型可采用小规模代表用例和人工评估；一旦处理真实用户数据、开放外部访问或自动执行高影响动作，必须按实际风险补足验证。每个 MUST 例外使用[例外模板](../../templates/artifacts/exception.md)，记录被覆盖风险、替代证据、负责人和到期时间。
