# 技术开发与代码规范

适用于人工和 Agent 提交的全部代码、配置、脚本、数据库迁移与生成资产。MUST 为适用要求，SHOULD 可按项目选择调整并记录原因，MAY 按需采用。语言细则由具体项目补充；本框架不绑定语言、目录分层或运行框架。

## 1. 可复现的开发环境

- **MUST** 在项目使用说明中写清安装、启动、构建、检查、测试的真实命令、运行时版本、必要外部服务和无秘密的配置示例。命令由项目实际技术栈提供；复制本文不代表已实现这些命令。
- **MUST** 提交适合该生态的依赖锁文件，并记录运行时、包管理器、构建工具和部署制品版本。应用默认使用冻结锁文件安装；库同时声明受支持的依赖范围并验证兼容性。
- **MUST** 在首次发布前从干净环境验证安装与构建，记录系统前提和结果。开发环境与 CI 的版本配置应同源。
- **MUST** 将开发、测试、生产配置分离；真实秘密不写入仓库、提示词、示例、测试快照或构建产物。新增环境变量说明用途、默认行为和是否敏感。
- **SHOULD** 提供一个聚合检查入口，并保证本地和 CI 使用相同检查定义；耗时较长的发布检查可以单独运行。

## 2. 可理解的模块与代码

- **MUST** 按稳定的领域能力划定模块边界，标明入口和对外接口。跨模块通过显式接口协作；访问另一模块内部实现应视为架构依赖变更。
- **MUST** 让命名与项目术语一致，同一概念不得在接口、数据库和文档中随意改名；需要映射时写明转换位置。
- **MUST** 在系统边界校验不可信输入，包括 API、事件、文件、用户内容与模型输出。类型声明不能替代运行时边界校验。
- **MUST** 清楚区分业务拒绝、认证/授权错误、暂时失败和程序缺陷；不得吞掉异常、返回伪造成功或用空数据掩盖依赖失败。
- **MUST** 对可能重复执行的副作用设计幂等、去重或明确的重复执行后果；时间戳、货币、精度与时区使用统一规则。
- **SHOULD** 将领域判断与 I/O 分开，使高价值规则可独立验证；先建立清晰接口，再考虑额外抽象层。
- **SHOULD** 注释解释约束、意图和不直观的选择。能由名字和类型说明的事实不重复注释；重要取舍链接 [ADR](../../templates/artifacts/adr.md)。
- **MAY** 在真实重复需求出现后提取共享能力；不得仅为假设中的未来项目增加插件体系或复杂通用框架。

## 3. 并发、依赖与性能

- **MUST** 外部请求设置超时；重试只用于可安全重试的情形，规定次数、退避与总预算。任务支持取消时，将取消信号传递到可中断的依赖。
- **MUST** 明确数据库事务、资源释放和并发更新语义；关键写入验证冲突、重复请求及部分失败路径。
- **MUST** 新依赖说明实际用途、来源、许可证与主要风险；禁止拼写近似包、来源不明下载脚本或未经检查的远程代码执行。
- **MUST** 面向公开输入的查询、上传、导出和批处理有资源限制，防止无界查询、无限循环、内存或费用失控。
- **SHOULD** 依据测量优化热点；性能变更保存可复现基线、输入规模、测量环境和比较结果。
- **MAY** 使用缓存、队列和异步任务；采用前需定义失效、顺序、重复、失败恢复和一致性要求，见[架构规范](architecture.md)。

## 4. 风格与自动化

- **MUST** 选择并提交该语言生态适合的格式化、静态检查和类型检查配置；不适用项写明原因。自动生成文件注明来源与生成命令，修正源文件后重新生成。
- **MUST** 检查配置变更与业务变更同样可审阅；不得通过删除断言、关闭规则、跳过必需任务或扩大忽略范围让失败“变绿”。
- **SHOULD** 优先使用官方或生态主流默认规则，减少无业务价值的格式争议；统一换行、编码和文件命名。
- **SHOULD** 将大规模纯格式调整与功能变更分开，便于审阅和回滚。
- **MAY** 对复杂或历史模块逐步收紧规则，但要给出收敛范围与负责人，不能无限期忽略新增问题。

## 5. Agent 参与开发

- **MUST** Agent 先阅读仓库指令、任务契约与相关代码，再修改；不同工具的指令适配按项目治理配置。
- **MUST** 任务明确目标、可修改范围、验收、已知约束和操作授权；Agent 对范围外的顺手重构另建建议。
- **MUST** 保留他人未提交变更；多 Agent 分工应声明文件/模块归属，集成负责人处理交叉依赖和冲突。
- **MUST** 审阅 AI 生成代码的行为、依赖、许可证风险和错误路径；“由 AI 生成”不构成降低标准或免于负责的理由。
- **MUST** 报告实际执行的检查及其结果。未执行、受环境限制、由模拟服务替代均需明示，不把计划写成已完成。
- **SHOULD** 高风险变更由独立的人或审阅步骤复核；同一模型自评可补充，但不能作为唯一风险证据。

## 6. PR 与完成条件

代码通过[开发生命周期](../handbook/lifecycle.md)进入评审。每个 PR **MUST** 指向对应 ticket/spec 或简化任务记录，解释触发问题、修改后行为、验证证据、兼容性影响及剩余风险。范围应足够聚焦，便于独立理解与回滚。

合入前检查：

1. **MUST** 实现覆盖适用验收条件，接口与必要文档同步；未完成内容作为明确任务记录。
2. **MUST** 运行受影响检查并处理失败；所需验证强度见[测试规范](testing.md)。
3. **MUST** 若涉及配置、权限、存储、迁移或外部接口，补充部署与恢复说明。
4. **MUST** 确认无真实秘密、调试后门或意外大文件，并遵循项目的审阅与合入权限。
5. **SHOULD** 在 PR 描述里提供便于复现的示例或截图，减少审阅者推测行为的成本。

## 7. 适用与例外

一次性脚本可只保留运行说明、输入边界和必要验证；纯文案变更不要求引入测试框架。项目的业务逻辑、共享接口和生产脚本不能因为代码量少而豁免输入校验、秘密保护和关键行为验证。MUST 暂时无法满足时使用[例外记录](../../templates/artifacts/exception.md)，注明负责人、影响、补偿措施和到期时间。

跨项目的共享包、契约和脚手架更新遵循[复用与升级](../handbook/reuse-and-upgrades.md)；不得直接复制一份实现后继续把两份代码称为同一版本。
