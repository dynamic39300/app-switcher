# UI、交互与视觉设计规范

本规范面向有用户界面的 Web、移动端、桌面端产品。纯 API 项目可声明不适用；CLI 仍应落实状态、错误和恢复语义。MUST 是适用范围内的要求，SHOULD 是可记录理由后调整的建议，MAY 是选项。采用档位与变更风险是两个独立维度，见[采用指南](../handbook/adoption.md)与[测试规范](testing.md)。

## 1. 开发前确定体验契约

以下 PRD/spec 指对应内容的权威位置，允许按[生命周期](../handbook/lifecycle.md)合并材料。新产品和新关键流程补齐体验契约；低风险已有界面修改可引用既有契约，在轻量变更中只记录差异。

- **MUST** 在 [PRD](../../templates/artifacts/prd.md) 中写明目标用户、首要任务、使用场景、成功标准，以及可收集哪些体验数据。成功标准应是任务完成率、错误率、完成时间等可观察结果。
- **MUST** 在 [spec](../../templates/artifacts/spec.md) 中记录关键流程、信息层级、状态转换和验收条件；涉及权限时标明角色可见内容和可执行动作。
- **SHOULD** 对新的关键交互先验证线框图或可点击原型。低风险已有组件的小改动可用截图和文字说明。
- **MUST** 为设计文件、组件实现、验收记录确定唯一有效版本及负责人；链接失效时应有仓库内截图或文字契约可供继续开发。

## 2. 状态覆盖

以下状态必须逐项判断是否适用。适用状态 **MUST** 有预期行为和验证证据；不适用可在 spec 的状态表中注明理由。

| 状态 | 必须回答的问题 |
| --- | --- |
| 初始、加载、刷新 | 等待什么？保留原内容还是显示骨架？多久提示超时？ |
| 空白、无搜索结果 | 是没有数据还是过滤无结果？用户下一步能做什么？ |
| 正常、成功 | 结果如何确认？是否需要下一步入口？ |
| 局部失败、整体失败 | 哪部分失败？已成功的操作是否保留？如何恢复？ |
| 离线、超时、限流 | 可以重试吗？是否会重复提交？草稿是否保留？ |
| 无权限、登录失效 | 给出可行动说明；不暴露无权查看的数据 |
| 禁用、只读 | 为什么不能操作？说明不能仅依赖悬停提示 |
| 编辑、未保存、冲突 | 离开会丢失什么？如何恢复或比较版本？ |
| 删除、撤销、恢复 | 影响范围是什么？恢复窗口和限制是什么？ |

- **MUST** 避免重复提交造成重复副作用；UI 的按钮禁用不能代替服务端幂等或去重。
- **MUST** 将表单错误关联到具体字段，用清晰文字说明修正方法，保留合法输入；错误不只通过颜色表达。
- **MUST** 对无法撤销的高影响动作，在执行前展示对象、范围和后果，并遵循[治理中的授权规则](../handbook/governance.md)。已有授权范围内的普通编辑不应反复确认。

## 3. 视觉系统与组件

- **MUST** 建立项目的语义 design tokens：背景、正文、弱化文字、边框、主要动作、成功/警告/错误，以及字体、字号、间距、圆角、层级、动效时长。值可先存在一个主题文件中。
- **MUST** 通用组件使用语义 token；业务页面不得以临时颜色替换状态语义。特例应有意图说明，并在复用时回收到系统。
- **SHOULD** 区分基础 token 与语义 token，例如 `color.blue.600` → `color.action.primary`；共享语义角色，允许不同产品采用各自品牌值。
- **MUST** 明确按钮、输入框、导航、弹窗、表格等实际使用组件的默认、悬停、焦点、按下、禁用、错误状态。
- **SHOULD** 优先复用已验证的组件库；引入新库需评估可访问性、维护状态、主题能力、许可与替换成本。
- **MAY** 在组件数量或协作成本增加时引入组件工作台、视觉回归、设计 token 自动同步。单页面项目不要求单独建设设计平台。

## 4. 响应式、内容与可访问性

- **MUST** 在 spec 中声明支持的设备、视口、浏览器及语言；验证最小/常用/最大支持宽度、长文本、空值和内容放大。断点应由内容布局需要决定。
- **MUST** 在支持范围内保证关键信息不被裁切、主要操作可达。复杂表格允许局部滚动，但不得把整个页面的必要阅读变成双向滚动。
- **MUST** 关键操作可通过键盘完成；焦点可见、顺序合理、不会被遮挡或困在控件里。弹窗打开后正确管理焦点，关闭后返回合理位置。
- **MUST** 使用语义化控件与可访问名称；图像按用途提供替代文本，表单有标签，错误和异步状态可被辅助技术感知。
- **MUST** 遵循项目声明的无障碍目标；本框架对面向用户的 Web 产品 **SHOULD** 采用 WCAG 2.2 AA 作为设计与验收目标。声明符合该等级前，必须对完整页面和完整流程完成对应范围验证。
- **SHOULD** 为文字、控件和焦点检查对比度；适用 WCAG AA 时普通文字至少 4.5:1，大字至少 3:1，并按标准定义与例外判断。尊重减少动效设置，避免仅靠动画传递进度。
- **MUST** 时间、时区、金额、单位和危险动作文案不产生歧义；内容使用产品领域术语，避免把内部报错栈直接展示给用户。

上述无障碍目标依据 [W3C WCAG 2.2](https://www.w3.org/TR/2024/REC-WCAG22-20241212/)；本清单是开发入口，不覆盖该标准全部成功准则，自动扫描通过也不能作为完整符合性证明。

## 5. AI 交互附加要求

适用于用户可见的生成、检索问答或 Agent 功能；开发者仅在编程时使用 AI，不触发这一节。

- **MUST** 区分排队、生成中、调用工具、待授权、完成、失败、取消、结果未知。模型“说完成”不能覆盖服务端实际执行状态。
- **MUST** 长任务提供取消入口并说明生效边界；取消后停止可停止的工作，已执行副作用要显示实际结果或待核实状态。
- **MUST** 流式内容可阅读、可复制且不持续抢占焦点；辅助技术应接收节制的状态播报，避免逐 token 播报。
- **MUST** 将“生成草稿”和“发送/发布/写入外部系统”作为独立动作表达；授权界面明确对象、参数和影响范围。
- **MUST** 当产品承诺提供依据时，显示可核验来源、引用范围及适用的时间信息；无依据或未核验内容要如实标明，不编造引用或精确置信度。
- **MUST** 允许用户修正输入、拒绝结果、恢复人工操作路径；仅当系统有真实撤销能力时显示“撤销”，否则说明补偿方式。
- **SHOULD** 在展示失败时说明重试是否计费、是否可能重复执行；长任务保留可恢复的草稿和进度。

这些是本框架的产品要求；工具授权和输出校验的实现见 [AI 工程规范](ai-engineering.md)。

## 6. 验收与裁剪

UI 变更合入前 **MUST** 留下：关键流程证据、适用状态检查、支持视口检查、键盘走查结果以及已知限制。低风险改动可在 PR 中记录；复杂流程使用[测试计划](../../templates/artifacts/test-plan.md)。

**SHOULD** 对主要用户任务进行屏幕阅读器抽查和真实用户验证；支付、身份认证、权限设置等高影响流程应提高验证深度。原型可减少视觉回归和设备矩阵，但真实用户使用的关键操作不能因“原型”标签而省略错误恢复和权限边界。MUST 的临时例外按[例外模板](../../templates/artifacts/exception.md)记录负责人、替代措施、失效日期及回补事项。
