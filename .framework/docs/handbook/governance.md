# 项目治理、责任与例外

## 责任分配

| 决策 | Accountable 最终责任 | 参与者 | 必要记录 |
| --- | --- | --- | --- |
| 目标、范围、验收 | 产品 owner | 用户、设计、工程 | PRD/spec 的 owner 与结论 |
| 技术边界、选型与契约 | 技术 owner | 开发、安全、运维 | 设计、必要 ADR |
| 质量与风险判断 | 交付 owner | 测试、工程、产品 | 风险等级、证据与遗留风险 |
| 发布与恢复 | 服务 owner | 运维、技术、产品 | 发布记录、runbook |
| 通用基线更新 | 框架维护者 | 试点项目 owner | RFC、验证、版本与迁移说明 |

MUST 为每个项目指定可联系的最终负责人；角色可兼任。Agent 可以执行或协助评审，最终组织责任属于指定的人或团队。个人项目可自审，但记录自审事实；高风险应引入独立复核或记录有时限的补偿。

## 工作节奏

SHOULD 按团队需要建立短周期节奏：需求分流 → 选出 ready 工作 → 限制进行中数量 → 交付演示 → 复盘。异步文档优先，只有存在冲突或重大决策时召开会议。跨项目依赖指定一个协调人、明确接口与交付条件。

MAY 使用 GitHub、Linear、Notion 等平台；在 `PROJECT.md` 指明需求、ticket、规格和知识库各自的权威位置。外部文档用于讨论时，accepted 决策必须能稳定链接并与版本关联；不可访问的私人聊天不是长期唯一依据。

## 例外与不适用

1. 先核对规则适用条件；确实不适用，写 N/A 和原因即可。
2. SHOULD 的替代方案在项目配置中记录理由。
3. 偏离适用 MUST 时填写 [例外模板](../../templates/artifacts/exception.md)：规则、范围、风险、替代控制、owner、决定者、期限、退出条件。
4. 到期复查：满足规则、续期并补新证据，或停止受影响能力。永久差异应反馈为规则改进，而不是无期限续期。

这套机制用于工程责任记录，不新增超出用户与组织既有权限的审批。任何例外不能覆盖法律、合同、安全平台权限或上层强制约束。

## 平台治理

MUST 在采用时区分“仓库文件存在”和“平台配置生效”。例如 CODEOWNERS 负责路由评审；强制 code owner review、分支保护、必需 CI、部署环境权限需要在 GitHub 实际配置。模板没有虚构账号，启用前由 owner 配置并验证。

新项目 SHOULD 使用短工作分支与小 PR；对长功能用 feature flag 或兼容切片。提交格式、分支策略与 squash 方式在项目配置里确定；没有自动发布需求时不强制复杂 commit 语法。

## 度量

选择少量能改变决策的指标：从 ready 到发布的周期、返工原因、逃逸缺陷、变更失败、恢复时间、用户结果；涉及模型再测任务成功率、延迟与成本。先形成项目基线，再设改进目标。不要按代码量、文档量、对话轮数比较人员绩效。
