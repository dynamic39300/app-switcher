# 设计原则与框架边界

本框架将 AI 纳入完整工程流程：人确定目标、约束和责任；Agent 在明确任务范围内研究、设计、实现与验证；工具提供权限边界与可复现检查。AI 的参与方式可以变化，产品正确性与责任不能外包给模型。

## 三层结构

| 层 | 权威位置 | 怎样改变 |
| --- | --- | --- |
| 通用基线 | 本仓库 `docs/handbook/`、`docs/standards/` | 有版本、证据与迁移说明的框架变更 |
| 项目配置 | 业务项目 `PROJECT.md`、`docs/project/` | 项目负责人决定；偏离 MUST 要登记例外 |
| 功能交付 | 业务项目 `docs/features/<feature-id>/`、实现、测试 | 变更 PR 同步规格、任务和证据 |

技术语言、云厂商、前端框架和管理平台属于项目选择。统一的是选型依据、边界与契约、文档语义、验证证据及演进方式。共享核心库可以减少重复实现，但不要求所有项目使用同一技术栈。

## 基本原则

1. **证据驱动**：提出问题时有场景或数据；声明完成时有版本与结果；研究分清事实、推断和建议。
2. **单一事实来源**：PRD 管目标、spec 管行为、技术设计管实现、ticket 管工作、测试管证据。通过 ID 和链接连接，不重复维护同一字段。
3. **按风险裁剪**：低风险修复可在一个工作单内完成全链路；高风险变更需要更多设计、验证和负责人参与。
4. **渐进披露**：根 Agent 文件只提供必要规则、入口和命令；按任务阅读具体规范。
5. **可执行优先**：能在配置、类型、契约和 CI 中执行的规则，逐步自动化；仅有文档的门槛明示为人工检查。
6. **小步交付**：用可测试的纵向切片验证关键假设；风险收敛后扩大范围。
7. **可逆与兼容**：发布有回滚或向前修复路径，迁移有数据恢复策略，跨项目依赖有版本。
8. **持续精简**：规范有负责人、复查日期和弃用路径；没有实践收益的规则可以删除。

## 规范性词语

- **MUST**：该场景适用时必须满足；暂时不能满足，按 [例外流程](governance.md) 记录责任、风险、补偿和期限。
- **SHOULD**：默认建议；项目可依据约束不采用，在项目配置中记录理由。
- **MAY**：可选能力；只有收益超过成本时引入。
- **不适用（N/A）**：适用条件不成立，例如 CLI 没有可视界面；须简述原因，与未完成区分。

这些词定义本框架内部约束强度，不表示获得外部认证。安全、隐私与可访问性规范同样需要按实际地区、行业和合同要求补充。

## 成熟度

`0.1.x` 为试用基线：已有模板和工具验证，待项目实践校正。至少经过不同类型项目的试点、完成升级演练并用交付数据评估后，再讨论稳定版。避免以文档数量、Agent 数量或代码行数评价成熟度。
