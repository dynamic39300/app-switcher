# 教学示例：产品更新邮件的订阅与退订

本目录是**未实现、未执行测试、未发布的教学材料**。角色、排期、技术方案和阈值均用于演示；仓库不存在对应业务代码、运行环境或真实 PR。所有执行证据保持待执行，发布状态为 `planned`。

示例选择一个表面简单、具有权限和副作用边界的功能：登录用户管理自己的产品更新邮件订阅，退订后阻止尚未开始发送的通知。目标是展示同一组需求如何贯穿材料，而非推荐一套必须采用的技术栈。

## 阅读与实施顺序

1. [PRD-001](prd.md)：为什么做、用户与非目标。
2. [SPEC-001](spec.md)：10 条验收条件、取消/重复/越权等行为。
3. [DESIGN-001](design.md)：UI、事务、发送边界与风险；再回校 Spec。
4. [TASKS-001](tasks.md)：6 个有依赖的切片，全部处于 backlog。
5. [QA-001](test-plan.md)：12 个计划用例，结果全部待执行。
6. [TRACE-001](traceability.md)：所有 AC 到任务、测试及 REL-001 的索引。
7. [REL-001](release.md)：发布与恢复计划，尚无制品或上线记录。

采用规则见[生命周期](../../docs/handbook/lifecycle.md)、[文档规范](../../docs/handbook/documentation.md)和[测试规范](../../docs/standards/testing.md)。创建业务项目时先使用[材料模板](../../templates/artifacts/README.md)，再按真实环境替换本示例的假设。

## 示例时间链路

下表是相对工作日的讨论安排，**不是承诺、工时实测或已经发生的事件**。阶段退出条件优先于日期。

| 计划窗口 | 活动 | 进入下一步的条件 |
| --- | --- | --- |
| D0 上午 | 问题证据与 PRD | 真实产品 owner 确认用户、范围、指标 |
| D0 下午 | Spec 草案；UI 与技术设计并行 | AC、权限、取消和发送边界清楚 |
| D1 上午 | 设计评审与第二次规格校准 | 消除关键 TBD，每条 AC 有设计去向 |
| D1 下午 | Tickets、用例、环境计划 | 契约、依赖、执行者和验证方法齐备 |
| D2 | TKT-001：偏好 API 与事务 | 真实检查支持契约、幂等和授权 |
| D3–D4 | TKT-002 发送门禁、TKT-003 UI；TKT-004 运行与验证设施并行 | 各自负责目录有可验收切片，共享契约保持一致 |
| D5 | TKT-005：集成、负向测试、恢复演练 | 所有适用风险检查与独立审阅通过 |
| D6 以后 | TKT-006：准备并执行发布 | 实际制品、授权、门禁和观察责任齐备 |

如果取消语义、供应商幂等或权限边界无法满足，应回到设计/Spec 更新范围和任务。不能为了按日历结束阶段把 backlog 改为 done。
