# QA-001：通知订阅验证计划

**教学/模拟；以下全部是待执行用例，没有任何通过结果。**上游：[SPEC-001](spec.md)、[DESIGN-001](design.md)；规则：[测试规范](../../docs/standards/testing.md)；结果索引：[TRACE-001](traceability.md)。

## 风险与环境

身份/租户隔离和邮件副作用使本变更风险为 high。计划采用独立审阅、授权负向验证、数据库竞态、故障注入、恢复演练及受控发布。该判断不要求机械增加所有测试工具。

使用隔离数据库、虚构 tenant-a/tenant-b 与 user-a/user-b/user-c，以及不会向公网发送的适配器测试替身。邮件标识使用保留示例值，例如 `user-a@example.invalid`。默认拒绝外部发送；真正供应商验证需要专用测试账号和明确范围。数据库事务验证使用真实测试数据库，测试替身不能证明真实邮件供应商的能力。

## 夹具与执行规则

每例独立准备主体与数据并清理；用可控时钟验证 24 小时和 30 天期限，用同步屏障控制竞态顺序。记录原始首次失败，不能以重跑成功隐去偶发竞态。测试替身模拟供应商明确接受、明确拒绝和结果未知，分别核对数据库终态与实际调用，而非只断言内部函数被调用。

对应命令将在真实项目实现；当前没有 `npm test` 等业务入口，不提供不可执行命令作为证据。采用后将项目的真实命令、版本和环境补入每次运行记录。

## 阶段门槛

- 本地/PR：运行受影响的 API/领域/集成与 UI 检查；权限、幂等、取消语义失败阻止合入。
- 候选：TKT-005 复核所有适用用例，独立安全审阅；执行暂停发送、回滚代码、保留退订记录的恢复演练；真实供应商语义待专门验证。
- 发布后：使用授权测试主体确认读取和退订路径，观察用户可感知错误与发送门禁；不向真实用户发测试邮件。
