# AppSwitcher 商业化：购买周期与续费规则研究

核验日期：2026-09-25。本文使用 Microsoft、JetBrains 和 Stripe 的第一方资料，区分厂商事实与本项目建议。内容用于下一阶段产品讨论，尚未成为已实现或已验收的行为契约；未进行支付交易或申请商户能力。

本轮用户已确认：首发服务中国大陆个人用户，大陆公司或个体工商户收款；先月、季、年主动付款续费，自动扣款及海外支付后置；账号不限制设备数量或类型。设备数量不参与下述计价，也不借并发规则变相限制设备。

## 行业做法及适用边界

| 来源与场景 | 官方核实的规则 | 能借鉴什么，不能据此推出什么 |
| --- | --- | --- |
| Microsoft 365：提前续费 | 提前续费不损失未使用时间，到期日按所选周期增加一个月或一年。[官方续费问题说明](https://support.microsoft.com/en-us/accounts-billing/subscriptions/problems-renewing-a-microsoft-365-subscription) | 支持“在原到期时间之后追加”。该页没有披露月末、闰年或跨周期内部算法。 |
| Microsoft 365：预付产品码 | 多个产品码增加使用期限，不增加安装数量或云存储；可叠加至最多五年。[官方产品码续费说明](https://support.microsoft.com/en-us/accounts-billing/subscriptions/how-to-renew-your-microsoft-365-subscription) | 预付续费和自动扣款是不同入口；期限可叠加。五年是其产品规则，不能当作行业通用或本项目已经确定的限制。 |
| JetBrains 个人订阅：主动续费 | 可在账号中手动提前续费；有效订阅用 Renew，已过期用 Resume payments，付款前核对价格。[官方续费说明](https://sales.jetbrains.com/hc/en-gb/articles/115001327130-Renew-a-personal-subscription) | 活跃续费和过期恢复都应有清楚入口。此页未给出提前续费的精确时间算法，不能单独证明从哪一秒起算。 |
| JetBrains 个人订阅：切换计费周期 | 单纯月付/年付转换在当前计费周期结束后生效；不同产品升级则是另一套处理，可将未使用部分抵扣新产品。[官方个人订阅变更说明](https://sales.jetbrains.com/hc/en-gb/articles/207737489-Make-changes-to-a-personal-subscription) | 同一权益变更购买周期，无须等同于功能升级。其描述是后续计费安排，不等于 AppSwitcher 已提前收款的年包；本项目可借鉴“保留当前周期”，不直接照搬扣款流程。 |
| JetBrains 个人月订阅：过期后恢复且允许中断 | 官方要求选择 continuity break（有此选项时），核对有效期从购买日开始，覆盖完整一个月；若显示追溯周期或空档收费，先联系支持。[官方过期恢复说明](https://sales.jetbrains.com/hc/en-gb/articles/38539348389266-Personal-license-Renewing-an-expired-monthly-subscription-with-a-continuity-break) | 过期恢复可以从新购买日起算，但这是一种明确选择，不能泛称所有 JetBrains 续费都不追溯。AppSwitcher 可直接选更简单的“不补收停用间隙”。 |
| Stripe Billing：自动订阅的日历锚点 | 月订阅以日期锚点计算；1 月 31 日对应 2 月 28 日（闰年 29 日），后续回到 3 月 31 日、4 月 30 日。文档明确考虑短月和闰年。[官方计费周期文档](https://docs.stripe.com/billing/subscriptions/billing-cycle) | 仅参考日历算法，不表示推荐中国大陆主体接入 Stripe，也不把自动订阅的账单、比例计费流程套到主动付费包。 |

**研究结论：没有一条统一“行业标准”涵盖所有续费情形。** 比较稳妥的共同设计是：剩余时长不作废，付款前显示结果日期，区分期限变更与功能升级，明确过期后是否补收空档。以下是结合 AppSwitcher 简单单权益产品所作的建议。

## 建议采用的首期规则

### 购买什么

- 月、季、年分别购买 **1、3、12 个日历月**，功能权益一致；年付优惠体现在价格，不影响剩余时间。
- “日历月”是从开始日期到后续月份对应日期，**不是固定 30 天，也不是每月 1 日到月底统一结算**。季度包是连续 3 个月，不是只能从 1/4/7/10 月开始。
- 每次购买都是一次主动支付，没有下次自动扣款。结账页用“购买一年”“续费一年”，避免“每月 ¥X”掩盖实际一次收取年费；折算月价只能作为辅助显示。

采用日历月能让用户理解“今天买，下个月这一天到期”。固定 30/90/365 天也可以实现，但必须明确按天售卖；本轮官方来源未证明哪种规则普遍占优，不宣称日历月是唯一行业惯例。

### 从何时开始计算

| 场景 | 建议结果 |
| --- | --- |
| 首次购买且没有剩余试用 | 支付经服务端核验、成功开通时开始，增加所购日历月数。不开通失败仍倒计时。 |
| 权益有效时提前续费 | 从原有效期终点继续增加所购月数；立即显示新的最终到期时间，不覆盖剩余期限。 |
| 月包仍有效时购买年包 | 追加 12 个月到原到期点，无须把剩余月包折价、退款再重买。年转月同理追加 1 个月。 |
| 已过期后重新购买 | 从本次成功开通开始新周期，停用间隙不补收费、不侵占新购买期限，并建立新的日期锚点。 |
| 还有完整功能试用时购买 | 建议保留试用剩余时间，在试用终点开始付费周期；最终以试用规则文档中统一确认的规则为准。 |
| 同一笔订单收到重复确认 | 只增加一次期限。订单成功页、客户端与账号中心读取相同权益结果。 |

“成功开通时刻”由服务端在核实真实付款后记录；不是浏览器跳转成功、客户端报告成功或用户提交付款截图。支付渠道付款时间与权益实际开通时间分别留存，以便处理迟到回调、故障补偿和争议。首付/过期重购不应因我们的发放延迟损失可用时间。

上述规则仅针对同一功能权益。若以后推出功能不同的版本，再单独设计升级差价；首期不引入复杂抵扣、余额或追溯重算。

### 日期、月末和闰年

建议统一以 **Asia/Shanghai（北京时间）** 计算日历周期，对外显示完整到期日期与时间；数据库保存确定的 UTC 时刻及计算依据。时区切换、设备换区、改本机时间不改变账号有效期。

持续有效的同一段权益保留首次开始的“目标日”和时分秒，并累计已购月数。目标月份没有该日，就临时取该月最后一天；以后月份恢复原目标日，**不要在每次续费时直接从裁剪后的 28 日继续相加**。中断后重新购买才重设锚点。

| 例子（全部北京时间） | 结果 |
| --- | --- |
| 2026-09-25 10:00 首次买 1 个月 | 有效至 2026-10-25 10:00；到达该时刻即到期 |
| 上例在 2026-10-10 提前买 1 年 | 最终有效至 2027-10-25 10:00，原来剩余半个月保留 |
| 已于 2026-10-25 10:00 到期，11 月 3 日 15:00 重购 1 个月并成功开通 | 新周期至 2026-12-03 15:00，不扣除 10/25 至 11/3 的间隙 |
| 2027-01-31 10:00 买 1 个月，并在到期前续 1 个月 | 第一段至 2027-02-28 10:00，连续续费后至 2027-03-31 10:00 |
| 2027-01-31 10:00 买 3 个月 | 至 2027-04-30 10:00 |
| 2028-02-29 10:00 买 1 年，之后连续按年续费 | 2029/2030/2031 年终点为 2 月 28 日 10:00；延续至 2032 年时回到 2 月 29 日 10:00 |

例子是 AppSwitcher 建议规则的演算，不是声称上述所有厂商都采用这些具体日期。订单应展示“本次购买时长、当前到期时间、购买后到期时间”；已过期或首次购买时展示预计开始时间，支付完成再给出实际结果。到期区间采用 `[开始时刻, 到期时刻)`，避免“一整天可用”与精确到期时间的表述冲突。

## 进入实现前需要写进验收的边界

1. 日期算法覆盖 28/29/30/31 日、大小月、闰年、连续月转年、过期重启周期；提前买 3 次月包与同一锚点买 1 次季包到期一致。
2. 预下单与付款之间，用户可能在另一设备续费；服务端按发放时的真实权益串行追加，不能拿旧到期时间覆盖已购期限。若结果日期变化，成功页显示实际更晚日期。
3. 多渠道通知、主动查单和人工补单必须复用同一订单身份，不能同一支付延长两次；两笔不同真实付款则分别记账，误购走退款流程。
4. 退款必须能关联到具体订单及它增加的期限；不能只修改一个没有来源记录的到期日期。退款比例、可申请范围及已使用期限如何处理，由售后规则统一确定。
5. 付费到期与网络验证失效是不同状态；离线宽限不能被当作额外购买周期，具体到期和离线体验由试用/离线规则统一定义。

当前尚未决定：具体价格、最大可预付跨度、促销赠送时长、价格调整时旧订单的待遇、未来自动扣款协议。不得把这些未决项做成用户已接受的限制。本文未改动生产代码，没有以文档检查代替支付或时间算法测试。
