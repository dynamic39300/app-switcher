# AppSwitcher 商业化：国内支付研究

核验日期：2026-09-25。本文是下一阶段的研究草稿，不代表支付能力已经开通、接入或通过验收。仅使用公开官方来源；未登录商户账户，未发起申请、交易、退款或部署。

## 已确认的产品方向

来自本轮用户讨论：先跑通 macOS 桌面产品及官网商业闭环，首发面向中国大陆个人用户，海外销售后置；收款主体拟为中国大陆公司或个体工商户，具体主体类型尚未最终区分。套餐按月、季、年由用户主动付款续费，自动按月扣款后置。国内希望支持微信和支付宝，相关账户正在申请。用户进一步确认同一账号不限设备数量、类型或同时在线数量；最新商业边界与建议规则见[里程碑](../../project/commercialization-roadmap-2026-09-25.md)和[规则稿](../../project/commercialization-rules-2026-09-25.md)。

**建议本期把“支付订单”和“软件使用权益”分开管理。** 官网下单，支付渠道收款，服务端确认后延长账号的使用期限，桌面端同步权益。用户付一次月费，不等于授权平台下个月自动扣费。

| 事实 | 对本项目的含义 | 官方来源 |

| 已有微信商户号的接入流程仍包含申请 Native 权限、公众账号认证及 AppID 与商户号授权绑定。 | “账户申请成功”不能直接作为官网支付上线的验收条件；需逐项确认产品权限和绑定状态。 | [微信 Native 开发接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015614538) |
| 支付宝商家中心将“电脑网站支付”“手机网站支付”“APP 支付”“当面付”等分列为产品，其中电脑网站支付用于商家网站收款。 | 官网结账优先核查电脑网站支付的签约和接入能力；不能把个人收钱码或其他场景的权限当作已具备该产品权限。 | [支付宝商家中心产品入口](https://b.alipay.com/signing/home.htm) |
| 微信普通支付接入流程包括服务端下单、支付回调、订单查询、关单、退款和下载账单。 | 收到钱并发放权益之外，还需要处理未付、超时、回调延迟、退款及账务核对。 | [微信 Native 开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791891) |

支付宝核验限制：本次可以读取官方产品入口，但电脑网站支付详情页抓取超时，新版 OpenDocs 页面未返回可读正文。因此，**支付宝扫码收银台的具体展示方式、当前签约条件及回调契约留待商户后台与可访问的当前产品文档核验**。不拿旧版“即时到账”接口或 AI 订阅专用方案替代本项目的准入依据。

## 本期方案建议（待 owner 确认后进入 spec）

1. 官网提供月、季、年购买选项，明确为一次性购买对应期限、到期主动续费。定价和折扣另外决定。
2. 结账前关联 AppSwitcher 账号。服务端生成订单及金额，微信走 Native；支付宝以电脑网站支付作为待验证方案。不要让用户根据付款截图人工激活。
3. 后端核验支付结果及订单归属后发放权益；客户端和网站都向自己的后端查询权益。支付私钥和商户凭据只保存在服务端。
4. 建议续费在 `max(当前到期时间, 确认生效时间)` 基础上增加购买期限，避免提前续费损失剩余天数；本轮新增建议为 1 / 3 / 12 个滚动日历月、保留连续期限的日期锚点、面向用户显示北京时间；[续费研究](renewal-rules-research-2026-09-25.md)给出月末、闰年与延迟发放示例，待评审后进入 spec。
5. 账号中心显示有效期、订单、续费入口及退款联系入口。当前没有自动扣费，不需要展示取消代扣按钮；提醒文案应避免写成“将自动续费”。
6. 支付完成而 App 暂时离线时，保留支付成功状态和恢复权益入口；避免让用户因同步慢而重复付款。离线宽限属于授权体验策略，具体时长由产品决定。

## 最小支付生命周期与验收建议

以下是本项目建议验收范围，不宣称已经实现或执行测试：

| 环节 | 最低可验收行为 |
| --- | --- |
| 创建订单 | 套餐、账号、金额和币种由服务端绑定；重复点击不会无提示地产生重复购买。 |
| 确认支付 | 验签并核对订单、商户身份、金额、币种及成功状态；前端伪造成功不能增加权益。 |
| 通知异常 | 重复通知只处理一次；通知延迟/遗漏可由查单补偿；已付款用户关闭浏览器仍能恢复权益。 |
| 支付中断 | 支付失败、取消、二维码过期时提供明确状态；关单与晚到成功通知的竞争有一致处理。 |
| 权益变更 | 一笔成功支付只增加一次期限；现有剩余时长不丢失；到期和重新续费行为明确。 |
| 退款 | 有退款申请与处理入口，记录独立退款状态；退款完成后按事先说明的规则调整权益，退款失败不假报成功。 |
| 对账与支持 | 定期将渠道账单与内部订单、退款、权益记录核对；能凭订单定位“已付款未开通”，补发操作有记录。 |

这些控制对应官方支付流程的现实边界：微信明确提供查单、关单、退款与对账，并要求对重复通知做好重入处理。[开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791891)、[回调通知](https://pay.wechatpay.cn/doc/v3/merchant/4012791882)。

## 开发前待商户后台核验

- 最终经营主体、结算账户与售卖内容：公司或个体的实际资质、软件工具对应经营类目、所需材料；不承诺任何主体必定获批。
- 微信：Native 产品权限、AppID 类型及认证、商户绑定、PC 网站经营场景审核、开发和回调配置。
- 支付宝：电脑网站支付签约、网页应用及上线状态、当前扫码方式、测试环境及生产交易权限。
- 费率、结算周期、交易限额、退款资金与手续费规则：以实际签约和商户后台为准，本研究不提供未经账户核验的数字。
- 域名、网站经营主体与部署地域确定后，再核实支付产品对网站备案/资质的要求，以及 ICP 备案等事项的适用范围；本研究不作“任何部署都需要/都不需要”的法律结论。
- 退款政策、发票/收据、隐私与用户条款及客服受理负责人要在收费前明确；具体法律和税务适用由负责人按经营主体与售卖地区核验。

## 海外范围的缺口

国内微信/支付宝方案不等于已经覆盖所有海外个人用户的付款方式、币种和售后需求。按用户最新决定，国际收款路线后置，本期不接入，也不将其作为上线条件；此前候选仅保留作未来研究。建议保持同一账号和权益系统，让各支付渠道只负责各自订单收款结果，订单明确币种与渠道，未来接入时重新核验准入和能力。

## 本次验证边界

完成公开文档研究与本地草稿编写；尚未验证任何真实商户的产品资格、费率、支付链路、退款链路或海外可用性。下一步先取得商户后台的能力核验结果，再定支付接口与验收计划；不需要等自动扣费能力才能建设本期主动续费闭环。
